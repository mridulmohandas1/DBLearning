WiredTiger Storage Engine (Default):

Journal files (unless journaling is disabled, which is not recommended). These are pre-allocated and created periodically.
Database Structure: While the data and indexes are in separate files, they are typically stored within a directory structure defined by the storage engine's configuration.

journal/ – Contains journal files for the MongoDB instance.
collection-*.wt – Stores collection data.

2) How journaling works 
How Journaling Works
Write-Ahead Log: Instead of immediately writing all changes to the main data files, MongoDB writes all modifications (write operations) to a special file on disk called the journal before they are applied to the core data files.
Sequential Writes: Writing to the journal is typically a fast, sequential operation, which minimizes disk seek time and improves performance compared to random writes directly to the main data files.
Commit Interval: MongoDB periodically flushes the in-memory changes to the journal file on disk. By default, this happens every 100 milliseconds (for the WiredTiger storage engine).
WiredTiger Storage Engine: Since MongoDB 3.2, the default storage engine is WiredTiger, which uses a combination of checkpoints and the journal (write-ahead log) for crash recovery. Checkpoints provide a guaranteed consistent state, and the journal covers the time period between the last successful checkpoint and the crash.

2.1) Commit vs check point?
In MongoDB, Commit and Checkpoint are two different operations in the WiredTiger storage engine. Commit makes a transaction durable, whereas a checkpoint persists a consistent snapshot of database changes to the data files.

4) What is Sharding, and How Does It Work in MongoDB?
Sharding is a method for distributing data across multiple servers in MongoDB. It allows for horizontal scaling by splitting large datasets into smaller, more manageable pieces called shards.
Each shard is a separate database that holds a portion of the data.
MongoDB automatically balances data and load across shards, ensuring efficient data distribution and high performance.

5) Explain the Concept of Replica Sets in MongoDB.
A replica set in MongoDB is a group of mongod instances that maintain the same data set.
A replica set consists of a primary node and multiple secondary nodes.
The primary node receives all write operations while secondary nodes replicate the primary's data and can serve read operations.
If the primary node fails, an automatic election process selects a new primary to maintain high availability.

6) How Does MongoDB Handle Data Consistency?
MongoDB provides several mechanisms to ensure data consistency:
Journaling: MongoDB uses write-ahead logging to maintain data integrity.
Write Concerns: It specify the level of acknowledgment requested from MongoDB for write operations (e.g., acknowledgment from primary only, or acknowledgment from primary and secondaries).
Replica Sets: Replication ensures data is consistent across multiple nodes, and read concerns can be configured to ensure data consistency for read operations.

9) Read and write concern?
Write concern determines how many replica set members must acknowledge a write before MongoDB considers it successful.
It controls durability and acknowledgement guarantees for writes.

✅ Common Write Concern Levels
writeConcern	Meaning
w: 0	        No acknowledgment — fastest, but no guarantee of durability.
w: 1	        Acknowledged by primary only — default in many cases.
j: true	 Wait for write to be written to the journal on disk.
w: majority	Wait until majority of voting members have applied the write — much stronger durability and reduces risk of rollback.
w: <number>	Wait for n members to acknowledge (e.g., w: 2).

You can also set :
	j: true — wait for journaling to disk,
	wTimeout — timeout for the write concern acknowledgment.

What Is Read Concern?
Read concern determines how “fresh” or committed the data must be before returning to the client — i.e., how up-to-date the read view is relative to writes.

🟢 Read Concern Levels
Level	Meaning
"local"	Returns the most recent data on that node, even if not yet replicated — fastest, default.
"available"	Least strict — reads whatever is there, possibly orphaned or rolled back data.
"majority"	Only returns data that has been replicated to a majority of the replica set — avoids reading data that could roll back.
"linearizable"	Strongest consistency — ensures the primary is still primary and data returned won’t be rolled back.
"snapshot"	Used with multi-document transactions to see a transactionally consistent snapshot across shards/replicas.

📌 Default:
Reads against the primary or secondaries use "local" unless overridden.

10) Sharding best practices?
1. Choose the Right Shard Key
The shard key is the most important design decision for sharding. A good shard key determines how evenly data and load are distributed.
Good shard key characteristics:
	High cardinality — many unique values helps spread data evenly.
	Uniform distribution — avoids hotspots where one shard does all the work.
	Even insert spread — avoids monotonically increasing values (like timestamps) which funnel writes to a single shard.
	Query targeting — queries should include the shard key to hit only relevant shards.
📌 Tip: Consider compound shard keys (multiple fields) if no single field meets all criteria.
2. Avoid Scatter-Gather Queries
Queries that don’t include the shard key must be broadcast to all shards (called scatter-gather) and degrade performance as the cluster grows.
Best practices:
	Always include shard key or an indexed prefix in filters.
	Use aggregation pipelines cautiously — large aggregations may still involve many shards.
3. Pre-Split and Balance Chunks
MongoDB divides data into chunks that are automatically balanced across shards. But for bulk loads or initial imports:
	Pre-split data so your shards start with nicely distributed chunks.
	Monitor the balancer and chunk migrations as your cluster grows.
This helps avoid performance dips caused by heavy balancing during peak write periods.
4. Use Appropriate Sharding Strategy
MongoDB supports three sharding strategies:
🌀 Hashed Sharding
	Good for uniform distribution and write scaling.
	Not ideal for range queries.
📈 Range Sharding
	Best when your queries are naturally range-based (e.g., date ranges).
	Requires careful key choice to prevent hotspots.
🌍 Zoned Sharding
Useful for geographically partitioned data — associate chunks with specific regions.

13) Incremental backup?
Method 1 — Using mongodump (Most Common)

Check:
	rs.status()
If standalone → convert to replica set first.

Step 2️⃣ Take Full Backup with Oplog
Run:
	mongodump --oplog --out /backup/full_backup
This: Dumps data
Captures Oplog at same time.This is your baseline full backup.

Step 3️⃣ Take Incremental Backup (Oplog Only)
Later, backup only new Oplog entries:
	mongodump --db local --collection oplog.rs --out /backup/incremental
This saves only changes.

🔄 Restore Process
Step 1:
Restore full backup:
	mongorestore --oplogReplay /backup/full_backup

Step 2:
Apply incremental oplog:
	mongorestore --oplogReplay /backup/incremental

If using tools from MongoDB Inc.: MongoDB Ops Manager / Cloud Manager provide:
	Automatic incremental backups
	Continuous point-in-time recovery
	Snapshot + oplog streaming
	No manual scripts needed.
🛠️ Method 3 — Using Filesystem Snapshots + Oplog
	Used in large production:
	Take disk snapshot (EBS/LVM)
	Archive Oplog continuously
This is fastest enterprise method.

13.1) Types of backup?

(PITR).
1. Types of MongoDB backups
Backup type	Description	Typical tool
Logical backup	Exports databases and collections logically	mongodump
Logical restore	Restores logical backup data	mongorestore
Filesystem backup	Copies MongoDB data files	OS-level tools
Storage snapshot	Captures storage volumes at a point in time	LVM, EBS, Azure Disk
Cloud-managed backup	Automated backup managed by MongoDB Atlas	Atlas Backup
Continuous backup	Supports recovery to a specific point in time	Atlas PITR / Ops Manager
Oplog backup	Captures operations for incremental recovery	Oplog replay

2. Logical backup – mongodump
mongodump is MongoDB's native logical backup utility.

Example:
mongodump \
  --host localhost:27017 \
  --username backupuser \
  --authenticationDatabase admin \
  --out /backup/mongodb/


Restore:
mongorestore \
  --host localhost:27017 \
  /backup/mongodb/


Characteristics:
- Backs up database and collection contents.
- Does not copy the original WiredTiger data files.
- Useful for database-level and collection-level backups.
- Can be used for migration between MongoDB environments.
- Generally slower for very large databases than physical snapshots.

3. Physical backup
Physical backup copies the actual MongoDB storage files, including WiredTiger data files and associated metadata.

Example:
mongod --shutdown
cp -a /data/mongodb /backup/mongodb/


Restore:
1. Stop MongoDB.
2. Restore the copied data directory.
3. Verify file ownership and permissions.
4. Start MongoDB.
5. Validate database and collection availability.
Characteristics:
- Copies actual database files.
- Generally suitable for large databases.
- Faster than logical backup in many large-database scenarios.
- Must ensure consistency between data files and journal files.
- Do not simply copy a running MongoDB data directory using ordinary file-copy commands and assume it is consistent.

4. Filesystem / Storage snapshot backup
A storage snapshot captures the underlying disk or volume at a particular point in time.

Examples:
- Linux LVM snapshots
- AWS EBS snapshots
- Azure Managed Disk snapshots
- SAN storage snapshots
Architecture:

Important: For a consistent snapshot, use an appropriate MongoDB-supported backup procedure. For replica sets, this can include filesystem snapshot coordination using a secondary or appropriate locking/quiescing procedure.

5. Oplog-based backup
MongoDB maintains an operation log called the oplog in the local database on replica set members.

The oplog records operations that modify data.

It can be used to recover a database to a specific point in time when combined with a suitable consistent base backup.

Example:
mongodump --oplog \
  --out /backup/mongodb/


Restore:
mongorestore \
  --oplogReplay \
  /backup/mongodb/


Important points:
- --oplog captures oplog entries during a replica-set dump.
- --oplogReplay replays those operations during restoration.
- Oplog retention determines how far back you can recover.
- This method is useful for achieving a more consistent backup and recovery point.

6. Incremental backup
Incremental backup captures changes since a previous backup rather than backing up the entire database every time.

For example:
Backup	Content
Sunday	Full backup
Monday	Changes since Sunday
Tuesday	Changes since Monday
Wednesday	Changes since Tuesday

MongoDB Enterprise backup solutions such as Ops Manager support incremental backup mechanisms.

MongoDB Atlas also provides managed backup capabilities, including point-in-time recovery depending on the cluster tier and configuration.
7. MongoDB Atlas backup
For MongoDB Atlas (managed MongoDB service), backup capabilities include:
- Automated snapshots.
- On-demand backups.
- Continuous backup.
- Point-in-time recovery (PITR).
- Backup retention policies.

17) What is workload isolation in Atlas
	Workload Isolation in MongoDB Atlas is a feature that lets you separate different types of database workloads onto different replica set nodes. This prevents one workload (such as analytics or reporting) from affecting another (such as transactional application traffic).
For example, if your application handles customer transactions while business analysts run large aggregation queries, those long-running queries can consume CPU, memory, and disk I/O. With workload isolation, you can direct the analytical queries to dedicated nodes, allowing the primary and other nodes serving your application to remain responsive.

	When you specify multiple field conditions in a query document, MongoDB implicitly combines them with AND.
Example
db.users.find({
    age: { $gt: 25 },
    city: "Bangalore"
})

	You explicitly use the $and operator when you want to combine conditions in an array.
Example
db.users.find({
    $and: [
        { age: { $gt: 25 } },
        { city: "Bangalore" }
    ]
})

When is Explicit $and Required?
Use $and when:
	You have multiple conditions on the same field that can't be expressed in a single operator object.
	You are dynamically building queries in your application.
	Your query structure requires combining separate condition objects.

21) Sequence of stages
If you're referring to MongoDB aggregation, the sequence of stages means the order in which aggregation pipeline stages are executed. The output of one stage becomes the input to the next.
For example:
db.orders.aggregate([
    { $match: { status: "Shipped" } },
    { $project: { customer: 1, amount: 1 } },
    { $sort: { amount: -1 } },
    { $limit: 10 }
])
The stages execute in this order:
	$match – Filter documents.
	$project – Select or reshape fields.
	$sort – Sort the remaining documents.
	$limit – Return only the first 10 documents.

36) What is database profile? 
MongoDB Profiler is a built-in feature that records information about database operations (queries, inserts, updates, deletes, commands) executed against a database. It helps you identify:

	Slow queries
	Collection scans (COLLSCAN)
	Long-running operations
	Frequently executed queries
	Query execution time
	Locking and resource usage
	Index usage
MongoDB supports three profiling levels.
| Level | Description                                           |
| ----- | ----------------------------------------------------- |
| **0** | Profiling disabled (default)                          |
| **1** | Log only operations slower than a specified threshold |
| **2** | Log every operation (use only for troubleshooting)    

Check the current profiling level:
	db.getProfilingStatus()
Example output:

{
    was: 1,
    slowms: 100,
    sampleRate: 1
}
was: current profiling level
slowms: slow query threshold in milliseconds
sampleRate: fraction of slow operations to capture (1 = all)

Enable Profiling
Level 1 (Recommended)
Log only slow operations.

	db.setProfilingLevel(1, {
    slowms: 100
})
Only operations taking more than 100 ms are recorded.

Level 2
Capture every operation.
	db.setProfilingLevel(2)
This is useful only for short-term diagnostics because it can generate significant overhead.

Disable Profiling
db.setProfilingLevel(0)

| Field          | Meaning                         |
| -------------- | ------------------------------- |
| `op`           | Operation type                  |
| `ns`           | Namespace (database.collection) |
| `millis`       | Execution time                  |
| `planSummary`  | Query plan used                 |
| `docsExamined` | Documents scanned               |
| `keysExamined` | Index keys examined             |
| `nreturned`    | Documents returned              |
| `ts`           | Timestamp                       |


The profiler stores its data in the system.profile collection within each database.

Queries taking more than 500 ms:

db.system.profile.find({
    millis: { $gt: 500 }
})

Sort by execution time:

db.system.profile.find()
    .sort({ millis: -1 })
    .limit(20)

Detect Collection Scans

One common use of the profiler is finding queries that are not using indexes.

db.system.profile.find({
    planSummary: "COLLSCAN"
})

Find Frequently Executed Queries
db.system.profile.aggregate([
    {
        $group: {
            _id: "$command.filter",
            count: { $sum: 1 }
        }
    },
    {
        $sort: { count: -1 }
    }
])

If you repeatedly see COLLSCAN, review whether appropriate indexes should be added.

## **Ops Manager Snapshot vs LVM Snapshot**

| Feature             | MongoDB Ops Manager Snapshot                           | LVM Snapshot                                              |
| ------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| Snapshot level      | MongoDB database data files                            | Block-device / logical-volume level                       |
| Technology          | MongoDB backup mechanism                               | Linux Logical Volume Manager                              |
| Initial snapshot    | Captures baseline database data                        | Creates snapshot of logical volume                        |
| Incremental changes | Tracks changed data-file blocks                        | Tracks changed disk blocks using COW or thin provisioning |

| Recovery            | Restore snapshot and optionally replay oplog           | Restore logical-volume snapshot

66) What is always atomic
MongoDB automatically guarantees that every operation affecting a single document is atomic, even without a transaction.
For example:
db.accounts.updateOne(
    { _id: 1 },
    {
        $inc: { balance: -1000 },
        $set: { lastTransfer: new Date() }
    }
);

Both updates happen together because they modify the same document. If the update fails, none of the changes are applied.

66) How mongodb decide operation should a transaction to not?
MongoDB doesn't automatically decide whether an operation should be a transaction. The application or developer decides.

	Case 1: No transaction (default)
		If your application executes normal operations:

	db.accounts.updateOne(...);
	db.accounts.updateOne(...);
	db.transactions.insertOne(...);

MongoDB treats each operation independently.
	First update commits immediately.
	Second update commits immediately.
	Insert commits immediately.
If the server crashes after the first update, the first change remains while the others may not occur.

	Case 2: Explicit transaction
		If your application starts a transaction:

const session = client.startSession();

session.startTransaction();

// Operations
db.accounts.updateOne(..., { session });
db.accounts.updateOne(..., { session });

session.commitTransaction();

Now MongoDB knows:
"These operations belong to the same transaction." It waits until commitTransaction() before making the changes visible. If something fails, abortTransaction() rolls back all operations.

67) Why MongoDB doesn't start transactions automatically
	MongoDB is optimized for performance. Starting a transaction for every operation would:
		Consume more memory.
		Hold locks longer.
		Increase replication overhead.
		Reduce throughput.
Since most MongoDB applications are designed so related data is stored in a single document, many updates are already atomic without the extra cost of a transaction.

| SQL Server                                                                            | MongoDB                                                                                              |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Transactions are common because related data is spread across many normalized tables. | Transactions are explicit and typically used only for multi-document or multi-collection operations. |
| Single `UPDATE` statements are transactional.                                         | Single-document operations are already atomic without starting a transaction.                        |
| `BEGIN TRANSACTION` is used frequently.                                               | `startTransaction()` is used only when multiple operations must succeed or fail together.            |


68) How to check transaction / operation per second?
Unlike SQL Server, MongoDB does not expose a built-in "Transactions Per Second (TPS)" counter because most operations are not transactions. Instead, you can measure either:
	Database operations per second (OPS) – reads, writes, commands.
	Multi-document transactions per second – only if your application uses transactions.

1. Check operation throughput (OPS)

Run:

db.serverStatus().opcounters

These are cumulative counters since the server started. To estimate operations per second:

Run the command.
Wait 10 seconds.
Run it again.
Calculate:
OPS = (New Counter - Old Counter) / Seconds

Example:

Insert:
10:00:00 -> 100,000
10:00:10 -> 100,500

OPS = (100500 - 100000) / 10
    = 50 inserts/sec

2. Check transaction statistics
	If your application uses multi-document transactions:

db.serverStatus().transactions

Important fields:

currentActive – Transactions currently executing.
currentOpen – Open transactions.
totalStarted – Total transactions started.
totalCommitted – Successfully committed.
totalAborted – Rolled back.

To calculate transactions per second:

TPS = (New totalCommitted - Old totalCommitted) / Time

Example:

10:00:00
Committed = 120000

10:01:00
Committed = 120900

TPS = (120900 - 120000) / 60
    = 15 TPS

3. Use mongostat (real-time monitoring)

Run:

mongostat

Typical output:

insert query update delete command
 120     40      30      2      600

This provides operations per second, refreshed every second by default.


4. Check current operations

To see active operations:

	db.currentOp()

Or filter only active ones:

	db.currentOp({
  	  active: true
	})

This is useful for identifying long-running operations but not for measuring TPS.

69) Should we check fragmentation and index rebuild periodically 
	MongoDB doesn't eliminate index fragmentation—it manages storage differently so that traditional index fragmentation maintenance (rebuild/reorganize) is generally unnecessary.

The reason lies in its storage engine, WiredTiger. MongoDB also uses B-tree indexes, but WiredTiger stores data differently. Instead of managing fixed 8 KB pages like SQL Server, WiredTiger:
	Uses variable-sized pages internally.
	Compresses index pages.
	Splits and merges pages automatically.
	Reuses freed space efficiently.
	Optimizes page layout as part of normal operation.

This greatly reduces the need for manual intervention.

70) How to achieve relation between documents or data?
MongoDB does not have foreign keys like SQL Server. Instead, relationships are modeled in one of two ways:
	Embedding (store related data inside the same document)
	Referencing (store the _id of another document)
Choosing the right approach is one of the most important aspects of MongoDB schema design.
	1. Embedding (Recommended for one-to-one or one-to-few)
		Suppose each customer has one address.
Instead of two tables like SQL Server, you store everything in one document.

{
    "_id": 1001,
    "name": "John Smith",
    "email": "john@example.com",
    "address": {
        "street": "10 Main St",
        "city": "New York",
        "zip": "10001"
    }
}
Advantages
Only one read is required.
Atomic updates (no transaction needed).
Excellent performance.
	2. Referencing (Similar to foreign keys)
		Suppose a customer can place thousands of orders.
Customers Collection

{
    "_id": ObjectId("64a1"),
    "name": "John"
}

Orders Collection

{
    "_id": ObjectId("9001"),
    "customerId": ObjectId("64a1"),
    "amount": 250,
    "status": "Completed"
}

Here,

Orders.customerId
        ↓
Customers._id

This is similar to a foreign key, but MongoDB does not enforce it.

	3. Joining data

MongoDB uses an aggregation stage called $lookup.

db.orders.aggregate([
{
    $lookup:
    {
        from: "customers",
        localField: "customerId",
        foreignField: "_id",
        as: "customer"
    }
}
])

Result

{
    "_id": 9001,
    "amount": 250,
    "customer":
    [
        {
            "_id": "64a1",
            "name": "John"
        }
    ]
}

Which indexes are used most?

For most MongoDB applications, you'll primarily work with:

Single Field Index – For simple lookups.
Compound Index – For multi-field filtering and sorting.
Multikey Index – For array fields.
Unique Index – To enforce uniqueness.
TTL Index – For automatic expiration.
Text Index – For full-text search.
Hashed Index – Mainly in sharded clusters.

The remaining index types—Partial, Sparse, Wildcard, and Geospatial—are more specialized and used when the application's data model or query patterns require them.

74) What is gridfs?

In MongoDB, GridFS is a mechanism used to store and retrieve large files, such as images, videos, audio files and PDF documents, that exceed the BSON document size limit.
The maximum BSON document size in MongoDB is 16 MB.
GridFS allows you to store files larger than 16 MB by splitting them into smaller chunks.
